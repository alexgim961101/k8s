Terraform으로 EKS를 한 단계씩 구축하기

1. Terraform과 EKS란 — 왜 같이 쓰는가

Terraform은 ‘땅(terra)을 만들다(form)’라는 이름처럼 인프라를 선언으로 만든다. Amazon EKS는 AWS가 control plane을 관리하는 Kubernetes 서비스로, 직접 관리해야 할 서버를 줄이기 위해 도입됐다.

이 실습의 경계

처음에는 공개 EKS module 대신 AWS 리소스를 직접 선언한다. 각 IAM role과 네트워크 경로를 이해한 뒤, 공개 module과 비교한다.

2. 책임은 세 층으로 나뉜다

EKS가 etcd와 API server의 가용성을 대신 관리하지만 node, VPC, IAM, add-on과 비용은 사용자의 책임이다. 이 문서는 node lifecycle을 AWS가 관리하는 Managed Node Group을 선택한다.

3. state를 격리해 실수의 반경을 줄인다

실습 코드는 이 저장소에 남기고, backend 예시는 Git에 남긴다. aws/lab/... key를 새로 써야 실습의 destroy가 운영 리소스를 향하지 않는다.

4. Pod가 이미지를 받기까지의 네트워크

실습용 network module에는 먼저 private subnet만 만들고 NAT/private route를 뒤에 추가한다. 워크숍은 먼저 이를 명시적으로 추가해 node가 ECR과 인터넷으로 나갈 수 있게 한다.

5. apply는 IAM → cluster → node 순서다

cluster role과 node role은 목적이 다르므로 분리한다. plan에서 기존 VPC가 replace되지 않는지, node group이 private subnet만 쓰는지를 매번 확인한다.

6. 사람의 kubectl 접근은 access entry로 준다

access entry는 legacy aws-auth ConfigMap보다 AWS API에서 권한을 관리하기 쉽다. kubectl auth can-i와 aws eks list-access-entries를 함께 확인한다.

7. 검증 후 destroy까지가 한 실습이다

terraform destroy는 실패가 아니라 재현성을 증명하는 마지막 단계다. 콘솔에서 수동으로 고친 리소스가 있으면 Terraform state와 실제 AWS가 달라질 수 있다.

8. 면접 질문으로 점검하기

Q1. EKS를 써도 내가 계속 관리해야 하는 것은 무엇인가?

control plane HA는 AWS가 관리하지만 VPC, node 용량, IAM, add-on, 워크로드와 비용은 사용자의 책임이다.

Q2. private node에 NAT가 필요한 이유는?

node가 ECR image와 add-on을 받기 위한 outbound 경로가 필요하다. private subnet이 public IP를 갖게 하려는 목적은 아니다.

Q3. cluster role과 node role을 분리하는 이유는?

assume 주체와 권한 목적이 다르다. 같은 넓은 권한을 주면 최소 권한을 지킬 수 없다.

Q4. 왜 aws-auth 대신 access entry를 쓰는가?

IAM principal과 EKS 권한을 AWS API·Terraform으로 함께 선언하고 복구 경로를 남길 수 있다.

Q5. 왜 destroy plan을 먼저 읽는가?

현재 state가 lab인지와 모든 유료 의존 리소스가 삭제 대상인지 확인한다.
