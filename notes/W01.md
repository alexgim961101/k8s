## 세션 1 (2h) — 환경 구축과 첫 클러스터

`notes/setup.md` 를 따라 도구를 설치한 뒤:

```bash
kind create cluster --config clusters/kind/study-cluster.yaml
kubectl get nodes -o wide
```

노드 3개가 `Ready` 가 되면 성공이다.

**여기서 한 번 멈추고 생각할 것**: 방금 `kind` 가 무엇을 만들었나?

```bash
docker ps                      # 노드가 사실은 컨테이너다
docker exec -it study-control-plane crictl ps   # 그 안에서 컨테이너가 또 돌고 있다
```

kind의 노드는 **kubeadm으로 구성된 컨테이너**다. W11에서 VM 위에 직접 kubeadm으로
클러스터를 세울 때, 지금 본 구조가 그대로 반복된다.

## 세션 2 (2h) — 클러스터 해부

컨트롤 플레인이 실제로 어디에 어떻게 떠 있는지 눈으로 확인한다.

```bash
kubectl get pods -n kube-system
kubectl get pods -n kube-system -o wide          # 어느 노드에 떠 있나?
docker exec study-control-plane ls /etc/kubernetes/manifests/
```

`/etc/kubernetes/manifests/` 의 YAML들이 **static pod** 다. kubelet이 API 서버 없이도
이 파일들을 읽어 컨트롤 플레인을 띄운다. (닭과 달걀 문제의 해법 — W11에서 다시 다룬다)

**정리할 것** — 각 컴포넌트가 죽으면 무엇이 멈추는지 한 문장씩:

| 컴포넌트 | 역할 | 죽으면? |
|---|---|---|
| kube-apiserver | | |
| etcd | | |
| kube-scheduler | | |
| kube-controller-manager | | |
| kubelet | | |
| kube-proxy | | |

> 표를 채운 뒤 실제로 확인해본다. 예: scheduler를 잠시 멈추면
> 기존 Pod는 계속 돌지만 새 Pod가 `Pending` 에서 멈춘다.

## 세션 3 (2h) — kubectl 기본기

**손에 익혀야 할 것** (속도가 나중에 CKA에서 그대로 점수가 된다):

```bash
kubectl get pods -A
kubectl get pods -o wide
kubectl describe node study-worker
kubectl logs <pod> -f
kubectl logs <pod> --previous          # 재시작 전 로그 — 장애 분석의 핵심
kubectl exec -it <pod> -- sh
kubectl api-resources                  # 이 클러스터가 아는 리소스 전체 목록
kubectl explain pod.spec.containers     # 문서를 검색하지 않고 필드를 찾는 법
```

**kubeconfig 구조 파악**:

```bash
kubectl config view
kubectl config get-contexts
kubectl config current-context
```

cluster(어디로) / user(누구로) / context(그 둘의 조합) 세 요소가 어떻게 묶이는지 확인한다.
W13에서 EKS 컨텍스트를 추가할 때 이 구조를 알고 있어야 헷갈리지 않는다.

**셸 설정** — 지금 해두면 16주 내내 이득이다:

```bash
echo 'alias k=kubectl' >> ~/.zshrc
echo 'source <(kubectl completion zsh)' >> ~/.zshrc
echo 'complete -F __start_kubectl k' >> ~/.zshrc
```

`k9s` 도 한 번 띄워본다. 탐색은 k9s가 빠르지만, **시험과 자동화는 kubectl이므로 kubectl을 주로 쓴다**.

## 세션 4 (2h) — 관통 프로젝트 컨테이너화와 배포

`CURRICULUM.md` §1의 관통 프로젝트를 정한다. 기존 프로젝트(`nestjs_test`, `my-todo-list` 등)를
가져와도 되고 최소 API를 새로 만들어도 된다. **조건은 하나 — 16주 내내 같은 것을 쓴다.**

```bash
docker build -t study-api:0.1.0 .

# kind 클러스터는 호스트의 이미지를 자동으로 보지 못한다. 명시적으로 주입한다.
kind load docker-image study-api:0.1.0 --name study

kubectl run api --image=study-api:0.1.0 --port=3000
kubectl get pod api -o wide
kubectl port-forward pod/api 3000:3000
```

브라우저나 curl로 접속되면 성공이다.

> **이미지 태그에 `latest` 를 쓰지 않는다.** `imagePullPolicy` 기본값이 태그에 따라 달라져
> 갱신이 안 되는 혼란을 겪게 된다. W10에서 정책으로 아예 금지시킬 것이다.

## 세션 5 (2h) — 반복 훈련과 체크포인트

**클러스터를 5회 부수고 다시 만든다.** 목적은 손에 익히는 것 + 재현 가능함을 확신하는 것이다.

```bash
kind delete cluster --name study
kind create cluster --config clusters/kind/study-cluster.yaml
```

이 반복이 W11~W12(구축·복구)와 W15(카오스)의 기반이 된다.
"부숴도 5분이면 돌아온다"는 확신이 있어야 과감하게 실험할 수 있다.
